# ADR-0009: Tailored CV PDF rendering with pdfkit

- Status: proposed
- Date: 2026-10-22
- Deciders: Rodrigo (product owner); Atlas (architect, review); Claude Code (Maestro, library choice);
  implementation Pêndulo (renderer), Alicerce (route), Vitral (download button)

## Context

The Career module (spec `docs/superpowers/specs/2026-10-22-cv-tailoring-design.md`) delivers, per job posting,
a tailored CV as a PDF (D3) generated by the API at download time (spec §4 and §5 item 7). D6 requires neutral
metadata, and §8 forbids any provenance marking (`original | rewritten | added`) in the PDF. Text must be
selectable, so applicant tracking systems and recruiters can copy and parse it, and Portuguese accents must
render.

The API has no PDF writer. A PDF library is a new runtime dependency of `apps/api`, which ADR-0001 requires
to be recorded.

## Decision

1. **pdfkit 0.20.2** (MIT, pure JS, published 2026-08-30) generates the PDF in-process: one A4 layout, no
   headless browser. It is pinned exactly in the pnpm catalog (two-week soak rule), with types from
   `@types/pdfkit` 0.17.6. Every new transitive package (fontkit 2, linebreak, restructure, fflate,
   `@noble/*`, …) was published more than 14 days before this ADR.
2. **The renderer is pure:** `renderTailoredCvPdf({ content: TailoredCvContent, base: CvStructured })` returns
   a `Buffer` and depends on nothing else (`apps/api/src/career/pdf/`). Contact, company, title, dates,
   education, certifications and languages come from the base CV by id. A dangling id rejects with
   `TailoredCvRenderError` before anything is drawn. Only `segment.text` is printed; provenance, ids and
   addition notes never reach the PDF.
3. **Fonts:** Source Sans 3 Regular and Semibold (Adobe, SIL OFL 1.1), versioned in `apps/api/assets/fonts`
   with their hashes. They are embedded as subsets (CID TrueType, Identity-H, with `ToUnicode`), so the text is
   selectable with accents and the standard 14 fonts are never used.
4. **Neutral, deterministic output.** pdfkit writes `Producer`/`Creator` = `PDFKit`, a `CreationDate`, an XMP
   packet repeating them, and a trailer `/ID` hashed from that date. The renderer empties the Info dictionary,
   skips the XMP packet and sets `/ID` to the first 16 bytes of a SHA-256 over the input. These three hooks are
   pdfkit internals; the pinned version and the tests (same bytes under two different clocks, no
   `Producer`/`Creator`/date/XMP in the bytes, a mutation that removes the hooks fails both) guard them on every
   bump.
5. **Tagged PDF:** structure tree (`Document`, `H1`–`H3`, `P`, `L`/`LI`), `/Lang` set to the posting language,
   rules marked as layout artifacts. This costs about 40 bytes and no measurable time, and helps screen readers
   and ATS reading order. It is not a PDF/UA conformance claim.
6. **File name:** `CV-<name>-<company>-<title>.pdf`. The name comes from `contact.name` of the base CV (never
   hard-coded) and company and title from the posting. Each part is reduced to ASCII letters, digits and
   hyphens and capped at 40 characters.

## Alternatives considered

- **pdf-lib 1.17.1** (the first proposal in the PR 3 plan). It has no release since 2021, and its last npm
  activity dates from 2022; the same holds for its font companion `@pdf-lib/fontkit`. Font subsetting has open
  bugs, and the library has no line breaking, so we would have to maintain word wrap and pagination
  ourselves. Its advantages: it can set metadata without touching internals (`updateMetadata: false`), and it
  can also edit existing PDFs, which this feature does not need. It is kept as the fallback if pdfkit stops
  being maintained.
- **Headless Chromium (Puppeteer/Playwright) with HTML templates.** This option gives rich layout, but it adds
  a ~150 MB browser to the API image and a sandbox to maintain, plus a renderer that runs HTML built from model
  output. It is out of proportion for one fixed layout.
- **Rendering in the worker and storing the PDF.** The spec renders on demand. Not storing files avoids a
  second copy of personal data (spec §8) and a cleanup path when a job or base CV is deleted.

## Consequences

- One new runtime dependency tree in the API (pdfkit, fontkit 2, linebreak, small pure-JS packages). About
  850 KB of font files go into the image. A typical CV renders in under 100 ms and weighs about 25 KB; a
  4-page fixture with 64 long bullets weighs about 37 KB.
- Upgrading pdfkit can break the metadata hooks silently at runtime, but not in CI: the determinism and
  metadata tests fail. A bump PR must keep them green, never relax them.
- Layout changes are code changes (one layout, spec §12: multiple layouts are out of this cycle).
- Sections of the base CV outside the tailored content (`other`) are not printed: the tailored content has no
  slot for them, and they are in the base CV language.

## Security / compliance impact

- The renderer only reads in-memory structured data; it does no I/O besides reading its fonts at module load,
  and it makes no network calls. Content is drawn as glyphs (hex glyph ids), so model output cannot inject PDF
  syntax. Links are printed as plain text, with no link annotations.
- Neutral metadata (D6): there is no tool identification, no creation or modification date, no XMP and no
  clock-derived `/ID`. The `/ID` does not reveal content: it is a truncated hash of the input.
- No provenance in the PDF (spec §8). This is tested on the extracted text and on the raw bytes.
- `TailoredCvRenderError` carries only the missing item id, never CV content (spec §8: no CV content in logs or
  Problem Details).
- The fonts are OFL 1.1: embedding and redistribution are allowed, and the license ships next to the files.
